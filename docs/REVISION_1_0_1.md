# ImportFlow v1.0.1 改修・再検証報告書

対象: 一次審査で再現したIF-PR-01・IF-PR-02

## 結果

**2件とも改修し、元の反例で解消を確認した。** 改修後のRust27件・フロントエンド4件はすべて成功。今回の検査対象2件は未解消のまま残っていない。Codexによる実装者自身の検証であり、独立した第三者監査ではない。

## IF-PR-01 / 利用者切替後の旧組織再表示

### 変更

- 現在のtokenを即時更新する参照を追加。
- loadの開始前にtokenと利用者世代を確認し、失効した処理が新しい利用者の読取世代を増やさないようにした。
- loadの結果・エラー反映前にもtoken・利用者世代・読取世代を照合。
- 取消等の変更後、detailをawaitした後にも利用者世代を再確認する。古いtokenを捕捉したloadへ進まない。
- 詳細読取も古い利用者からの呼出しでは開始しない。

### 確認

同じAppコンポーネントを使い、取消の応答→詳細待機→管理者Bへの切替という元の反例を3回実行。各回、B選択中のAジョブ表示なし、切替後のAによるsummary/jobs/catalog要求0、終了コード0。改修前は3回とも表示あり・旧組織3要求・終了コード1だった。

回帰試験は`web/tests/role-race.test.mjs`として通常のnpm testへ組み込んだ。実React DOM・jsdom・制御fetchによる試験であり、実ブラウザー通信でタイミングを再現したという意味ではない。

## IF-PR-02 / 期限切れ整理のロックによる取得停滞

### 変更

- 期限切れ・試行上限の候補を、先にFOR UPDATE SKIP LOCKEDで取得。
- 整理対象は1回最大50件。ロック中の行を待たず、別の待機ジョブの取得へ進める。
- failedへの更新と監査は同じ取引で実行。

### 確認

元の実DB反例を3回成功。期限切れジョブ行を別取引で保持したまま、別のqueuedジョブを取得した。ロック解除後は期限切れジョブをfailedへ整理し、その監査は1回だけ。繰返し呼出しでも監査を重複作成しない。

追加試験では55件の期限切れを1回目50件・2回目5件で整理し、failed監査は55件のまま。元の取得反例は`review_claim_skips_locked_exhausted_job`、件数制限は`expired_cleanup_is_bounded_and_not_repeated`として通常の統合テストへ追加した。

350msは試験の観測期限であり、全運用状況で350ms以内を保証するSLAではない。修正対象は行ロック待ちの回避で、DB全般の遅延や外部DDLの影響をなくすものではない。
